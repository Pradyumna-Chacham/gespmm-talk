## 1. GE-SpMM Retuned

Introduce ourselves and the project. We took GE-SpMM, a 2020 paper that showed a hand-written CUDA kernel could beat NVIDIA’s own library at sparse times dense matrix multiplication, and we rebuilt it on a current GPU. The question we set out to answer was simple: five years and three GPU generations later, do the tricks in that paper still work? The answer turned out to be more interesting than yes or no, and most of this talk is about what we found when we went looking for the reason.

## 2. SpMM: multiply a sparse matrix by a dense matrix

Let me start with what this operation is and why anyone cares. In a graph neural network, every layer updates a node by mixing its own features with the features of its neighbours. If you write that mixing step as linear algebra, it is exactly a sparse matrix multiplied by a dense matrix, which people call SpMM. The sparse matrix A is the graph itself: a one wherever two nodes are connected, and zeros everywhere else, which is almost everywhere. The dense matrix B is the feature table, one row per node and N columns, where N is the feature width; we test N from 16 up to 512 because that is the range real models use. The result C is the updated features. This matters because it is where the time actually goes: the paper profiled GCN training and found this single operation is about thirty percent of it, on all three of their graphs. The last point is the one to remember for the rest of the talk. This kernel does very little arithmetic per byte it reads, about half a flop per byte, so it is limited by how fast the GPU can pull data out of memory. On our card that ceiling is around 224 gigaflops. Every optimization in this talk is about moving less data or hiding the time spent waiting for it.

Backup (if asked): If asked where the numbers come from. The thirty percent is Table I of the GE-SpMM paper, measured with a profiler during GCN training: 33.1 percent on Cora, 29.3 on Citeseer, 29.8 on Pubmed. The 224 gigaflop figure is our card’s 448 gigabytes per second multiplied by roughly half a floating-point operation per byte. It is a bandwidth ceiling, which is the important part: no amount of arithmetic tuning gets you past it, so every result in this talk comes from moving data better, never from doing less maths.


## 3. How the Matrix Is Stored: CSR

Before the tricks, you need to know how the matrix is stored, because the storage format decides what the kernel can and cannot do. This is CSR, compressed sparse row, and it is just three arrays. Storing all sixteen entries of this little matrix would be wasteful, and for a real graph with millions of nodes it is impossible, so we only keep the non-zeros. The val array holds the non-zero values, read row by row, left to right. The colind array holds the column each of those values came from. And rowptr marks where each row begins in the other two arrays: row zero occupies entries zero and one, row one is entry two, row two is entries three and four, row three is entries five and six. To get row zero of the answer you look up rowptr, find that row zero has two non-zeros, read their values five and two and their columns one and three, and then the answer is five times row one of B plus two times row three of B. That is the single most important sentence on this slide: one output row is a weighted sum of a few rows of B, and the column indices tell you which rows of B to pick up. Everything the GPU kernel does is about fetching those rows of B efficiently. And this should look familiar: it is the same CSR format and the same y = A·x kernel from homeworks one to four. SpMM is just N of those SpMVs sharing one A.

Backup (if asked): Two things if asked. This four by four matrix is our own teaching example, not from the paper; real graphs in our test set run from a thousand rows to nearly five million. And if someone asks why the storage format matters so much: almost every faster sparse kernel in the literature converts the matrix into some other layout first, and GE-SpMM’s whole selling point is that it does not. It reads these three arrays exactly as a graph library already stores them, so there is nothing to convert and nothing to amortise. Our kernel keeps that property, which is why we never compare against preprocessing-based kernels.


## 4. The Paper We Started From

This is the paper we rebuilt. GE-SpMM was published at Supercomputing in 2020. Its selling point was compatibility: there were already faster sparse kernels in the literature, but they all required converting the matrix into a special layout first, and in a graph neural network you often multiply by a given graph only a handful of times, so the conversion costs more than it saves. GE-SpMM works directly on the CSR arrays we just saw, with no conversion at all, and still claimed to beat NVIDIA’s own cuSPARSE library. It does that with two tricks, which the next two slides explain properly. The first, coalesced row caching, is about the thirty-two threads of a warp cooperating on one fetch instead of all asking for the same thing. The second, coarse-grained warp merging, is about squeezing more output out of each thing you fetch, controlled by a number they call the coarsening factor, CF, which the paper fixes at two for every matrix. Remember that it is fixed, because that is one of the things we change. On the right is the hardware gap we are testing across: they ran on Pascal and Turing cards with CUDA 10.1; we ran on a Blackwell card with CUDA 12.9, plus four older GPUs so we could see how the answer changes by generation.

Backup (if asked): If asked about the figures on the left: those are the paper’s own headline numbers, against cuSPARSE’s csrmm2 routine and against GraphBLAST, measured on their two cards. We are not disputing them; on the older GPUs we reproduce the same ballpark. If asked why we used a 5060 Ti rather than a datacentre card: it is what was available on ARC, and the point of the study is the gap between generations rather than absolute speed, which is why we ran the same binary on four more GPUs spanning Pascal, Turing, Ampere and Ada.


## 5. Trick 1: Coalesced Row Caching

Here is the first trick, and the table at the top is the whole idea. One warp, thirty-two threads, works on one row of the output, and each thread is responsible for one column. Now look at what a single thread needs in order to handle one non-zero of that row. It needs the value, it needs the column index, and it needs one entry out of B. The first two are identical for all thirty-two threads: every thread in the warp is walking the same row of A. Only the third differs, because each thread is working on a different output column. So the sparse side of the data is shared and the dense side is private, and that asymmetry is what both tricks exploit. Without the trick, all four threads in my picture go to memory and ask for the same address, which is wasteful, and they do it again for every single non-zero in the row. With coalesced row caching, the four threads instead fetch four different non-zeros in one single request, which the hardware can serve as one transaction, drop them in shared memory, and then everybody reads from shared memory, which is fast and on-chip. Fetch once, use it thirty-two times. One thing to flag now because it comes back later: this row only has two non-zeros, so two of my four threads had nothing to fetch and sat idle. On real graphs most rows are shorter than thirty-two, so that cooperative fetch is often half empty.

Backup (if asked): If asked how much this trick is actually worth, do not pre-empt slide ten, just say: in our implementation it is still a win on every GPU we tested, about eight percent on Blackwell and twenty-five to thirty percent on the older cards, and there is a slide coming on why that shrank. The idle-lane point is measured rather than hand-waved: we track the fraction of rows with fewer than thirty-two non-zeros as a matrix feature, and it is one of the five numbers our run-time selector uses to choose a setting.


## 6. Trick 2: Coarse-grained Warp Merging

The second trick covers the other way you can end up paying twice. Coalesced row caching fixed the waste inside one warp. But suppose the output is wider than the warp — say eight columns when I only have four threads. The obvious thing is to use two warps, the first covering columns zero to three and the second covering four to seven. The problem is that both of those warps have to walk the same row of A, so the values and column indices get fetched from memory twice, for the same answer. Coarse-grained warp merging says: don't do that. Use one warp, and give each thread two running totals instead of one. Thread zero now owns column zero and column four. When it fetches a non-zero, it immediately uses it for both of its columns before throwing it away. The row gets fetched once instead of twice. The number of columns per thread is the coarsening factor, CF, and the paper picked CF equals two and used it for every matrix and every feature width. The intuition behind a larger CF is obvious: more reuse per fetch. The cost is less obvious, and we will come back to it — each extra column means another running total in registers, and a wider slice of B in flight at once.

Backup (if asked): If asked about larger coarsening factors, we did sweep four and eight. Across seven hundred and five measured cases, four was the best choice seven times and eight was best three times, so they are not useful in practice on this hardware. Be honest about one gap: four and eight have the same loop shape as one and two, but they are not covered by the line-by-line compiler ablation on the later slide, which only tested one and two, so we do not claim anything about them there.


## 7. What We Re-implemented, and Changed

So what did we actually build. We rewrote the paper’s two kernels from the algorithms in the paper, as a single templated kernel, which compiles into a hundred and twenty variants that we choose between at run time. Then three changes. First, a correctness bug. Their index arithmetic is thirty-two bit, which is fine for the graphs they tested, but once the number of rows times the feature width goes past roughly two point one billion, the index wraps round and the kernel quietly computes wrong answers. There is no crash and no warning; you just get bad numbers. Ours uses sixty-four bit offsets, and separately, every single timed run we report is checked against a double-precision reference first, so nothing gets timed unless it is correct. Second, and this is the part I want you to take away: the paper fixes the coarsening factor at two for every matrix in the world. We pick it per matrix, using a rule you can say out loud. Use CF equals two only if the average row is short, four entries or fewer; otherwise use one. And whenever the row lengths are very uneven, use one. Both of those numbers come from a single cheap pass over the rowptr array, so we never even look at the matrix values. On twenty-seven matrices the rule was never fitted on, it lands within half a percent of the best choice you could have made with hindsight, where the paper’s fixed two is about three percent off at wide outputs, and twenty-six percent off at narrow ones. One distinction to have straight in case you are asked, because these are two different things. That rule is the explainable version, and it is the one I would quote, because you can say it out loud and check it. What actually ships in the library is a small model: three-nearest-neighbour over a shortlist of six settings, using five cheap numbers about the matrix and the feature width — average row length, how uneven the rows are, the output width, the share of rows shorter than thirty-two, and the matrix size. Alongside it one hand-written rule looks at the unevenness and sends the worst matrices to a different kernel entirely. Picking costs about a quarter of a millisecond, paid once per graph, and in a graph neural network you multiply by the same graph thousands of times, so it is free in practice. That selector is where the one-point-one-four times figure on the takeaways slide comes from. Third, we wrote a CPU version in OpenMP, which is the next slide.

Backup (if asked): Backing detail if pushed. The overflow is not hypothetical for their own test set: the largest graph in the paper’s benchmark suite has four point eight five million rows, and at a feature width of five hundred and twelve that is two point four eight billion, past the two point one five billion a signed thirty-two-bit index can hold. The rule’s scores come from a held-out test: the rule is fitted on the training matrices only and scored once on twenty-seven matrices it never saw, including every citation graph and every synthetic power-law graph as whole families. The 0.995 is a geometric mean of how close it lands to the best coarsening factor available in each case, and its worst single case is 0.95.


## 8. Why We Also Wrote a CPU Version

This is the slide where the CPU version earns its place, so let me be clear about why it exists. It is not here so we can say a GPU is faster than a CPU; everyone knows that. It is a control. Here is the puzzle. This kernel slows down a lot on uneven graphs, where a handful of nodes have thousands of neighbours and most have two or three — which is what every real social or web graph looks like. There are two possible explanations. One: it is the GPU’s fault, because one row is assigned to one warp and that assignment is baked in when the kernel launches, so a warp that draws a huge row cannot hand it off or split it, and a warp that finishes early cannot go and help. Two: it is the algorithm’s fault, and any row-by-row sparse multiply would suffer the same way on any hardware. The problem is that you cannot tell these apart using GPU measurements, because every GPU measurement has warps baked into it. The only way to separate them is to run the same algorithm on hardware that has no warps at all. That is the CPU version. The numbers are in the table: on the same uneven matrices, the paper’s GPU mapping keeps thirty-one percent of the throughput it had on an even graph, and the CPU keeps eighty-two. So the penalty belongs to the execution model. One honest caveat I want to say out loud: we expected dynamic scheduling to be the reason the CPU copes, but static and dynamic come out within one percent of each other, so that is not the explanation. The CPU simply holds up either way.

Backup (if asked): Backing detail if pushed. These are synthetic matrices from a grid where we set the average row length and the unevenness independently, so the only thing changing between cells is the shape of the graph. Each number is that series compared against its own even-graph cell, so we are not comparing a GPU against a CPU directly, we are comparing how much each one loses. The effect is strongest at narrow outputs and milder at wide ones: the GPU row-split mapping keeps 0.31 at width 16 but 0.79 at width 512, while the CPU stays around 0.82 to 0.90 throughout. If asked why our tuned GPU version only recovers to 0.62, the merge-path kernel claws back about seventy per cent of the gap at width 16, not all of it.


## 9. Our CPU Kernel vs Intel MKL

Since we built a CPU version, the obvious question is whether it is any good, so we measured it against Intel MKL, which is Intel’s own hand-tuned maths library and the fair thing to compare against. The table is time ratios, so below one means we are faster. At the narrowest output, sixteen columns, MKL beats us by about ten percent — their short-row handling is better than ours. At thirty-two we are ten percent ahead. From sixty-four columns upward we are consistently around thirty to forty percent faster, on the same machine with the same sixteen threads. Two things underneath that. First, scaling: we get about six and a half times on sixteen threads at the widest output. I want to be careful about how that number is read, because it is tempting to fit Amdahl’s law to it and announce a serial fraction. That would be wrong here. This processor has two chiplets, and the step you see between eight and sixteen threads is the second chiplet’s memory link becoming available, not the code getting more parallel. Second, the roofline. At wide outputs we reach about twenty-seven percent of what the machine could theoretically attain, and MKL about twenty-one. Neither is close to the ceiling, and when we counted the actual traffic it was roughly four times the minimum the problem requires. So the thing limiting us at wide outputs is re-reading the B matrix, not raw memory bandwidth and certainly not arithmetic.

Backup (if asked): Backing detail if pushed. These are the runs after short-row packing became our default, which is itself worth twelve to sixteen per cent at the two narrowest widths. The scaling figures are two, four, eight and sixteen threads giving 1.91, 3.05, 3.85 and 6.35 at width 512, with threads bound close to their cores. The reason the curve flattens between four and eight and then jumps is that this processor has two chiplets and up to eight threads share one chiplet’s memory link, which we measured separately: a STREAM-style benchmark gives 125 gigabytes per second across sixteen threads but only about 63 on one chiplet. If asked why MKL still wins at width 16, the honest answer is that we do not know — we never profiled it to see which routine it picks. That is on the last slide as unfinished work.


## 10. Why the Tricks Looked Dead

This is the slide I would most like you to remember, and it is a story about being wrong. Our first campaign found that the authors’ coalesced-row-caching kernel was forty percent slower than their own simple kernel on the new GPU, and we had a tidy explanation: Blackwell has a thirty-two megabyte cache, the cache is now doing by itself what the trick used to do by hand, so the trick is obsolete. It is a nice story and it is wrong. Two things killed it. First, we ran the same experiment on a 4060 Ti, which has exactly the same thirty-two megabyte cache, and there was no gap at all. If the cache were the explanation, that card should behave the same way. Second, the hardware counters: the slow kernel moves exactly the same bytes, gets the same cache hit rates, has the same occupancy and actually executes slightly fewer instructions. It was not doing more work. It was waiting — twice as many stall cycles per instruction. The real cause is the compiler. Their inner loop has two exit conditions, stop at the end of the thirty-two-entry tile or stop at the end of the row, and to unroll a loop like that the compiler has to reason out the trip count. For every GPU generation from Pascal through Ada it does. For Blackwell it silently does not, and you can see it in the machine code: sixty-eight load instructions become eight. Unrolled, eight loads go out together and their memory latencies overlap. Rolled, every single non-zero waits for its own load. We rewrote three lines of their source and their kernel became as fast as ours. So the honest conclusion is the opposite of what we first reported: with well-compiled code, coalesced row caching still wins on Blackwell. The benefit shrinks, from twenty-five or thirty percent down to eight, but it does not turn into a loss.

Backup (if asked): Backing detail if pushed. The three lines are: the two-exit loop bound; a test that asks “am I the last column block” instead of “do I stick out past the end”, which sends every last block down the bounds-checked path even when nothing sticks out; and a bounds check written once per non-zero instead of once per tile, which the compiler keeps as a real branch so the loads cannot be batched. Every fixed version produces bit-identical output to ours, same summation order, so this is not a numerical trade. Worth knowing: __restrict__, which is the usual first guess, makes no measurable difference here, under nought point three per cent. The damage is worst on skewed graphs, where one warp walks thousands of non-zeros and pays a full memory latency for each: wiki-Talk and com-Youtube are 4.2 times slower at width 16. One caveat to volunteer: we only tested CUDA 12.9, and we did not try the compiler the paper originally used.


## 11. Takeaways

Pulling it together. The first takeaway is the one with the broadest reach, and it is a methodological one: when you re-run an old GPU paper on new hardware, you are measuring the compiler at least as much as the algorithm. We had a clean, plausible hardware story — bigger cache makes the trick redundant — and it was wrong, and it took a second GPU with the same cache size and a look at the machine code to find that out. Second, the first trick survives, just smaller: it still wins on Blackwell, by eight percent instead of twenty-five. Third, the second trick’s fixed setting does not survive. Across seven hundred measured cases the paper’s choice of two was the best one less than half the time, and at any feature width of sixty-four or more our grid says one, everywhere, without exception. Fourth, you do not need a complicated model to fix that — a rule reading two cheap numbers off the matrix gets within half a percent of perfect on matrices it has never seen. Fifth, the CPU control answered its question: uneven graphs cost the GPU far more than the CPU, so that penalty is about how GPUs execute, not about the algorithm. And finally the two numbers at the bottom, which I want to be careful about. Tuned per matrix with hindsight we are fifty-eight percent faster than the best cuSPARSE. But the number that means anything in practice is the one on the right: fourteen percent, with our selector choosing blind on graphs it had never seen. That is the honest headline and that is the one we quote.

Backup (if asked): Backing detail if pushed. The 1.58 is a geometric mean over the 115 matrices that have both timings at width 512, with 112 outright wins and three losses, and a confidence interval of 1.50 to 1.68. The 1.14 is our auto policy measured on the 27 held-out matrices, 159 samples; it compares kernel times taken from two different runs, so a few per cent either way should not be over-read. One number to have ready in case someone digs: the learned selector on its own, without the rule that routes very uneven matrices to the merge-path kernel, scores 0.98, which is slightly below cuSPARSE. It is the combination that wins, not the model alone, and we would rather say that ourselves than have it found.


## 12. Future Scope / Next Steps

Where this goes next, and what we have not done. First, the compiler result is solid but incomplete: we can show that the unrolling decision changes between architectures and we can show the consequence, but we have not traced which specific heuristic inside the compiler changed, and we only ever tested one CUDA version. It would be worth checking whether the paper’s own compiler behaved this way. Second, our line-by-line ablation covers coarsening factors one and two; four and eight have the same loop shape and should behave the same way, but we did not measure them, so we should not claim them. Third, MKL beats us at the narrowest output and we do not know why — we never profiled it to see which routine it picks or where its time goes. Fourth, an honest negative: we tried to choose the merge-path settings from matrix features the same way we choose the coarsening factor, and nothing generalised. Every version we tried did worse than a plain hand-written rule, and even a perfect choice in every case would only reach ninety-two percent, so we report that as a limit rather than quietly dropping it. And fifth, housekeeping: six of our figures still come from the first campaign’s kernels and should be regenerated, and the question of whether reordering the graph’s vertices helps was never measured at all. The closing thought is the one from the previous slide: the tricks do still work, but a constant someone chose in 2020 and a compiler released in 2025 each turned out to matter more than the algorithm itself.

Backup (if asked): Backing detail if pushed. On the merge-path negative: we tried a per-width table, a table that could also pick the two-kernel variant, a nearest-neighbour model over the same features, tables split by matrix size, and an extra longest-row feature. On the held-out matrices these scored between 0.831 and 0.887, against 0.880 for the plain hand-written rule, so none of them earned its place. The ceiling matters too: even choosing the best merge setting in every single case would only reach 0.917, and the best setting changes from case to case, so no rule over these features can predict it. That is why we present it as a limit of the approach rather than a thing we ran out of time on.
